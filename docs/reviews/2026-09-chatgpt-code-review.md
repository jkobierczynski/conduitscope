# External code review: ChatGPT, September 2026

This is an unedited, externally produced review, kept here as a primary
source rather than folded into the main documentation. Jurgen asked
ChatGPT to review the ConduitScope repository (reading the actual C++
source, not just the README) and shared the output here for a second
opinion. See [DEVELOPMENT.md](../DEVELOPMENT.md)'s "External code review
and engineering priorities" section for the response to it, what was
verified against the repository, and the resulting priority order.

The line counts and commit numbers below reflect the state of the
repository at review time (before this file was written, and before some
subsequent work); see DEVELOPMENT.md for current figures.

---

I went considerably deeper into the repository this time. I also checked the actual raw C++ rather than relying on the README.

My assessment is substantially more nuanced than "43k lines generated by AI in three days."

## Bottom line

ConduitScope is a surprisingly substantial prototype.

I would not classify it as 43k lines of AI-generated fluff.

There is real engineering in it: protocol framing, layered reassembly, collision handling, malformed-input handling, state tracking, policy evaluation, inventory inference, PCAP/PCAPNG parsing, and a fairly extensive regression corpus.

At the same time, I would not call it production-grade OT security software yet. The architecture has some very obvious consequences of rapidly expanding a codebase with AI: a huge central decoder, repeated utility logic, enormous comment density, broad protocol surface with uneven depth, and a testing strategy that is strong in breadth but still mostly black-box regression testing.

And frankly, doing this in three days is the most remarkable part of the project.

## 1. The actual architecture

The first thing I noticed is that the project has a reasonably sensible high-level decomposition.

The CMake target currently contains roughly this structure:

```
conduitscope_core
│
├── capture / framing
│   ├── pcap_reader
│   ├── link_layer
│   ├── ipv4
│   ├── tcp
│   └── udp
│
├── industrial protocols
│   ├── modbus
│   ├── dnp3
│   ├── iec104
│   ├── enip
│   ├── profinet
│   ├── goose
│   ├── sv
│   ├── ethercat
│   ├── devicenet
│   ├── bacnet
│   ├── hartip
│   ├── ffhse
│   ├── opcua
│   ├── mms
│   ├── mqtt
│   ├── s7comm
│   └── s7commplus
│
├── IT / infrastructure protocols
│   ├── DNS
│   ├── NBNS
│   ├── TLS/SNI
│   ├── routing protocols
│   ├── STP
│   ├── EAPOL
│   └── various IT recognition
│
├── analysis
│   ├── decoder
│   ├── resolver
│   ├── asset_inventory
│   ├── policy
│   └── policy_engine
│
└── presentation
    ├── output
    ├── CLI
    └── YAML
```

That separation is actually quite good for something produced this quickly.

The CMake file lists around 40 implementation units, rather than one gigantic source file.

So the project isn't structurally equivalent to someone asking an LLM:

"Make me an OT packet analyzer"

and getting a 43k-line monolith.

## 2. But there is a giant architectural bottleneck

This is the biggest architectural weakness I see.

decoder.cpp is currently 2,892 lines, while decoder.hpp is 1,239 lines.

That's enormous for something whose primary responsibility should theoretically be:

parse packet → identify protocol → invoke decoder → produce result.

The header also contains a very large ProtocolFilter enum covering essentially the entire protocol universe of the application.

And the implementation contains a long ordered chain resembling:

```
OPC UA
 ↓
EtherNet/IP
 ↓
IEC104
 ↓
Modbus
 ↓
DNP3
 ↓
S7/COTP
 ↓
HART-IP
 ↓
MQTT
 ↓
FF-HSE
 ↓
...
```

with extensive collision-specific logic.

That's understandable for a protocol analyzer, but it creates a God Object / central dispatcher problem.

Every time you add a protocol, decoder.cpp grows.

Every protocol can potentially affect another protocol's detection.

And eventually you get:

"Adding protocol X requires modifying protocol X plus the central decoder plus tests plus protocol-filter enumeration plus output structures."

That's where this architecture will start fighting you.

### I'd eventually replace that with a registration model

Something conceptually like:

```cpp
struct ProtocolDecoder {
    virtual DetectionResult detect(ByteSpan data,
                                   const DecodeContext&) const = 0;

    virtual DecodeResult decode(ByteSpan data,
                                const DecodeContext&) const = 0;
};
```

Then:

```cpp
registry.register_decoder(ModbusDecoder{});
registry.register_decoder(Dnp3Decoder{});
registry.register_decoder(OpcUaDecoder{});
```

with explicit detection priority/confidence.

That would make the architecture scale much better.

But I wouldn't waste three days doing that now.

For a v0.1 project, the current architecture is perfectly understandable.

## 3. The protocol work is much more serious than the LOC initially suggested

This is where I changed my opinion most strongly.

Take DNP3.

dnp3.cpp alone is 963 lines.

And this isn't just:

```cpp
if (payload[0] == 0x05)
    protocol = "DNP3";
```

The implementation handles:

data-link framing, CRC, transport sequence, FIR/FIN, application fragments, object headers, object groups/variations, binary inputs, analog inputs, counters, output commands, quality flags, timestamps, multi-frame reconstruction.

The tests go after precisely the ugly stuff.

For example, the test suite explicitly checks:

multi-block CRC, corrupted header CRC, corrupted block CRC, source/destination station addresses, DNP3 fragment continuation, sequence mismatch, orphan continuation, stale reassembly, coalesced DNP3 frames, real capture CRC validation.

That's real protocol-engineering work.

AI can write it, obviously.

But the specification knowledge and testing targets still have to come from somewhere.

## 4. Your TCP reassembly is actually quite thoughtful

This was another thing I didn't expect.

The TCP layer doesn't simply concatenate packets.

`Decoder::reassemble_tcp_payload()` tracks sequence numbers and distinguishes:

expected next segment, retransmission/overlap, complete duplicate, missing segment/gap.

The implementation explicitly trims overlapping retransmitted bytes rather than blindly appending them.

For example, it recognizes a fully overlapping segment and ignores it rather than feeding duplicate application bytes to the protocol decoder.

It also has a bounded state approach for things like DNP3 and COTP fragments.

That's exactly the kind of thing that makes packet analysis substantially harder than simply parsing Ethernet/IP/TCP headers.

### But there's a limitation

Your reassembly is capture-order based, rather than being a full TCP reassembly engine.

When it sees a forward sequence gap, it abandons the current PDU:

"TCP sequence gap ... abandoning an in-progress ... reassembly"

rather than maintaining an out-of-order segment map and reconstructing later.

That's a perfectly defensible design for an audit tool where you want to avoid inventing data.

But it means:

ConduitScope isn't equivalent to Wireshark's TCP stream reconstruction.

And I think that's the correct choice for your stated philosophy:

Don't claim what the capture doesn't actually establish.

I'd keep that behavior, but make the limitation very explicit.

## 5. Your "don't hallucinate the packet" philosophy is one of the strongest aspects

This is probably my favorite engineering characteristic of the project.

There are numerous places where the code explicitly chooses:

I'd rather say "unknown / incomplete" than make up a protocol interpretation.

The DNP3 reassembly code is a particularly good example.

If a continuation arrives without the beginning: application layer not decoded, rather than reconstructing something from arbitrary bytes.

Likewise, sequence mismatch causes the buffered fragment to be discarded.

That is exactly what I want from a security/audit tool.

False certainty is substantially worse than incomplete decoding.

## 6. You are also actively dealing with protocol collisions

This is where the source gets interesting.

The decoder explicitly discusses real collisions such as: IEC-104 vs Modbus, DNP3 vs Modbus, HART-IP vs Modbus, FTP vs MQTT, and LDAP vs MQTT.

For example, the Modbus parser has a sanity limit around MBAP length because you encountered traffic where unrelated bytes could satisfy `protocol_id == 0`.

The code even documents that the false-positive behavior was observed in actual captures.

That's good engineering.

It's also something that strongly suggests this wasn't simply an LLM hallucinating protocol parsers in isolation.

You appear to have been feeding failures back into the implementation.

## 7. Modbus is relatively small — and that's actually good

modbus.cpp is only 278 lines.

That's because you're not pretending to implement every possible corner of Modbus.

It handles meaningful functions such as 01–04 reads, 05/06 writes, 15/16 multiple writes, exceptions, and uses transaction ID + TCP session tracking to pair requests and responses.

The particularly good bit is that the code acknowledges that some Modbus messages are shape ambiguous.

For example, write-single request/response have the same structure.

Instead of pretending the payload itself can distinguish them, the decoder uses transaction/session state to establish the direction.

That's exactly the sort of distinction I would expect from a serious analyzer.

## 8. The PCAP reader is better than I expected

pcap_reader.cpp is 429 lines.

It handles: classic PCAP, endian variants, nanosecond timestamps, PCAPNG, multiple PCAPNG sections, interface descriptions, timestamp resolution, enhanced packet blocks, simple packet blocks, unknown block skipping, sanity limits, malformed block detection.

And it deliberately skips unsupported PCAPNG blocks instead of treating them as fatal.

That's a reasonable implementation strategy for an offline analyzer.

One thing I'd flag: you deliberately don't support PCAPNG Packet Block.

That's documented rather than hidden, which is good. But this becomes an interoperability issue worth testing against a corpus of weird captures.

## 9. The testing is considerably stronger than the GitHub project age suggests

This is perhaps the biggest surprise.

The CMakeLists.txt is 5,523 lines, and an enormous proportion of that is test registration.

The tests aren't just: program returns 0.

They're checking specific decoded semantics.

For example: DNP3 CROB: Latch On, Close, count=1, on_time=1000ms, status=Success, and exact CRC behavior.

There are also tests for inventory → generated policy → policy validation round-tripping.

That's excellent because it tests the actual product workflow, not just individual functions.

## 10. But your testing architecture is also one of the biggest weaknesses

Most of those tests are CTest tests invoking the CLI and matching output using `PASS_REGULAR_EXPRESSION`.

That's useful, but it's a form of black-box snapshot testing.

For example:

```
COMMAND conduitscope decode ...
PASS_REGULAR_EXPRESSION "..."
```

This gives you excellent regression protection for user-visible behavior.

But it doesn't tell you: branch coverage, memory safety, sanitizer findings, parser invariants, property correctness, fuzz resilience, internal state correctness.

And there's a second problem: your test suite is gigantic inside CMakeLists.txt.

That's going to become painful.

I'd move toward:

```
tests/
    unit/
    protocol/
    integration/
    corpus/
    fuzz/
```

and use GoogleTest/Catch2/doctest — or even your own tiny test harness if you want zero dependencies.

## 11. The most glaring missing thing: CI

The repository currently has 59 commits, zero issues and zero PRs, and the source itself explicitly says there is no CI configured yet.

For a security/network-analysis application, this is the first thing I'd fix.

Especially because you're supporting GCC, Clang, Linux, potentially Windows, optional libpcap, multiple protocol paths.

I'd immediately add: Ubuntu + GCC, Ubuntu + Clang, ASan, UBSan, Release build, Debug build, CTest.

Then later: clang-tidy, cppcheck, `-fsanitize=address,undefined`, `-fsanitize=fuzzer`.

The absence of CI doesn't make the code bad.

But it means you don't yet have an automated mechanism proving that today's AI-generated code still works tomorrow.

## 12. The AI fingerprints are extremely obvious

I don't mean this negatively.

There are strong signs of AI-assisted development in the source.

The biggest indicator isn't syntax.

It's the comment style.

There are huge comments explaining: why a helper exists, why another helper wasn't shared, what a previous bug looked like, why protocol A is tried before protocol B, what collision was observed, why a particular safety cap exists, what the test immediately below is proving.

For example, decoder.cpp repeatedly contains comments of the form: "Tried LAST...", "see the matching comment...", "this codebase's own research found...", and extremely detailed explanations of individual heuristics.

Likewise, asset_inventory.cpp contains very elaborate explanations for its heuristics.

That is very AI-like code-generation style.

But here's the important distinction: AI-looking ≠ bad.

In fact, some of those comments are useful.

The problem is that comment volume becomes disproportionate to the actual code, and eventually the comments themselves become another maintenance burden.

I'd eventually cut perhaps 30–50% of the commentary and retain comments only where they explain: why this seemingly strange thing is necessary.

## 13. There is some unnecessary duplication

I noticed this in particular: policy_engine.cpp has `session_key(...)`, while asset_inventory.cpp independently has essentially the same canonical TCP session-key logic.

The code even explains why it is duplicated.

That's a classic AI-generated-code characteristic: "Keep each engine self-contained."

It sounds reasonable, but over time it creates divergent implementations.

I'd extract `FlowKey`, `SessionKey`, `EthernetFlowKey` into a small common networking/state utility.

Likewise, protocol naming/filter registration appears to be spread through multiple places.

This will become increasingly painful as the protocol count grows.

## 14. DecodedPacket is becoming too large

The 1,239-line header is the giveaway.

You're putting fields for practically every protocol into one universal result object.

Conceptually:

```cpp
DecodedPacket
    modbus_*
    dnp3_*
    iec104_*
    enip_*
    profinet_*
    goose_*
    ...
```

This works.

It's also simple for JSON output.

But it doesn't scale elegantly.

Eventually I'd move toward something like:

```cpp
struct DecodedPacket {
    CommonPacketMetadata common;
    Protocol protocol;

    std::variant<
        ModbusResult,
        Dnp3Result,
        Iec104Result,
        ...
    > decoded;
};
```

or a polymorphic result object.

That would dramatically reduce the central coupling.

Again, don't refactor it yet unless you're actively hitting the pain.

## 15. Inventory is clever, but you correctly call it heuristic

asset_inventory.cpp is 589 lines.

The inventory engine does something useful:

```
PCAP
 ↓
observed OT endpoints
 ↓
communication relationships
 ↓
inferred zones
 ↓
generated policy
 ↓
policy validator
```

That's a genuinely interesting workflow.

But the code itself correctly acknowledges that some decisions are heuristic.

For example, treating an IPv4 address ending in .255 as a broadcast address is explicitly described as a heuristic because the actual subnet mask isn't necessarily known.

That's exactly how I would want it documented.

### The danger

Users will inevitably interpret `inventory` as: "This is my OT architecture."

It isn't.

It's: "This is the OT architecture that can be inferred from this observation window."

I'd make that distinction absolutely unavoidable in the CLI output and documentation.

## 16. The policy engine is probably the most commercially interesting component

The policy engine is 715 lines.

This is where ConduitScope starts becoming something different from "another packet decoder."

The basic pipeline is:

```
Observed traffic
        ↓
Protocol semantics
        ↓
Zone/conduit classification
        ↓
Allowed communication policy
        ↓
Compliance result
```

That is a useful abstraction.

Wireshark/tshark can tell you: "PLC A sent a Modbus Write Multiple Registers to PLC B."

Your engine can potentially answer: "PLC A → PLC B is not an authorized conduit."

That's the actual product differentiation.

And your inventory feature then goes in the opposite direction:

```
unknown network
      ↓
inventory
      ↓
draft segmentation model
      ↓
human review
      ↓
policy
      ↓
audit
```

That's a pretty good product loop.

## 17. One thing I would not do: keep adding protocols

This is where I'd push back hard if you were asking me as an engineering lead.

You already have a ridiculous protocol surface for a three-day project.

The README currently advertises everything from Modbus/DNP3/S7 through IEC-61850, OPC UA, MQTT/Sparkplug, routing protocols, remote-access recognition, enterprise authentication protocols and more.

At this point: another 15 protocols will probably add less value than making the existing ones trustworthy.

I'd prioritize: 1. fuzzing, 2. CI, 3. sanitizers, 4. PCAP corpus, 5. protocol correctness, 6. performance benchmarks, 7. memory/state limits, 8. reproducible reports, 9. architecture cleanup, 10. only then additional protocols.

## 18. The most important security concern

Because this is a security tool parsing attacker-controlled packets, your threat model is unusual.

The input is effectively hostile.

So the key question isn't: "Does it decode my sample PCAP?"

It's: "Can I give it a deliberately malicious 4 GB PCAP containing pathological protocol fields and make it crash, hang, allocate 20 GB RAM, or produce a false audit result?"

You have already added some useful safety caps: maximum packet size, maximum PCAPNG block size, maximum protocol fragments, maximum DNP3 buffered bytes, maximum transaction tracking, maximum message counts.

That's good.

But this should become a systematic resource-budget architecture, rather than individual caps added as problems arise.

## 19. What I would do next if this were my codebase

I'd freeze feature development temporarily.

### Phase 1 — make it hostile-input safe

Run: ASan, UBSan, MSan where practical, Valgrind, libFuzzer, AFL++ against every protocol.

Especially: pcap reader, TCP reassembly, COTP, DNP3, S7, OPC UA, MMS, MQTT, EtherNet/IP, IEC104.

The protocol parsers are exactly where fuzzing can pay off.

### Phase 2 — create a corpus

I'd maintain:

```
tests/corpus/
    modbus/
    dnp3/
    s7/
    iec104/
    enip/
    opcua/
    mqtt/
    ...
```

with: clean, malformed, truncated, fragmented, retransmitted, corrupted, ambiguous, real-world captures.

Then every bug becomes: PCAP + regression test.

That's much more valuable than another 5,000 lines of code.

### Phase 3 — CI

Minimum: GCC Debug, GCC Release, Clang Debug, Clang Release, ASan/UBSan, CTest.

Then: clang-tidy, cppcheck, coverage, fuzz smoke tests.

### Phase 4 — architecture

Only after the behavior stabilizes: ProtocolRegistry, ProtocolDecoder, DetectionResult, DecodeResult, FlowKey, SessionKey, and shrink decoder.cpp.

I'd aim to turn 2,892 lines into something closer to 500–800 lines of orchestration.

## 20. My engineering assessment

If I were reviewing this internally, I'd describe it approximately like this:

| Area | Assessment |
|---|---|
| Overall architecture | Good prototype architecture |
| Protocol breadth | Exceptional for project age |
| Protocol depth | Very uneven |
| TCP/reassembly | Surprisingly thoughtful |
| Defensive parsing | Good instincts |
| Testing breadth | Very good |
| Testing depth | Needs fuzz/property testing |
| Code organization | Reasonable, but central decoder is too large |
| Maintainability | Currently moderate |
| Documentation | Very strong, perhaps excessively verbose |
| AI-generated-code risk | High, but mitigated by testing |
| Production readiness | Not there yet |
| Product concept | Actually quite interesting |

And I'd give the project one particularly important distinction:

This is not a toy because it was written by AI.

The source demonstrates actual attempts to deal with the hard parts of network analysis.

The question that remains is whether the breadth was purchased at the expense of correctness.

That's what fuzzing, independent protocol validation and a much larger real-world PCAP corpus need to establish.

## And now back to your original three-day question

After seeing the source, I'd revise my original estimate again.

For the current codebase, I would put conventional human development at roughly: **~1,500–3,500 engineering hours** to reproduce the current breadth and functionality from scratch.

Possibly more if the developer had to independently research all the protocol details and build the test corpus.

And your actual contribution was: **~3 days of human-directed development.**

That's an extraordinary compression ratio.

But I'd phrase the achievement carefully:

You didn't manually write a 43,000-line C++ program in three days. You architected, specified, tested and iteratively directed an AI to produce a surprisingly broad OT network-analysis codebase in three days.

And after actually examining the source, I think that's considerably more impressive than I initially assumed.

The next interesting question isn't "how many hours would this take a human?"

It's "how much of the 43k LOC is actually doing useful work, and where are the 10–20 most dangerous correctness assumptions?"

That's the review I'd do next, because I can already see several places where ConduitScope's architecture is making assumptions that could materially affect an OT audit result.
