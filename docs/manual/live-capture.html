Manual / Live capture & continuous capture

Live capture & continuous capture

Two different jobs: decode -i (and info/policy validate/inventory/detect with -i) analyze a live interface directly, one pass, in-process. capture does the opposite -- it only records, to disk-bounded rotated classic-pcap files, meant to run unattended for weeks, with analysis as a separate later pass.

Passive-mode guarantee

conduitscope never transmits anything onto the wire, in any mode -- no ARP, no probes, no replies, nothing. See USER_GUIDE.md's PASSIVE-MODE GUARANTEE for how to verify this yourself (e.g. with an isolated span port and a packet counter) if that matters for your deployment.

Permissions: CAP_NET_RAW (Linux) / admin (Windows)

bashGrant the built binary CAP_NET_RAW once, root never needed again

$sudo apt install -y libcap2-bin
$sudo setcap cap_net_raw,cap_net_admin=eip build/conduitscope

# every run after this, by any user, opens -i without sudo:
$build/conduitscope decode -i lo --duration 2
capture on 'lo' stopped (0 packet(s) captured)
PowerShellNpcap driver + an elevated shell

# install the Npcap runtime/driver (separate from the build-time SDK -- see setup.html)
# from https://npcap.com/#download, then run from an elevated PowerShell/cmd session:

PS>build\Release\conduitscope.exe interfaces
PS>build\Release\conduitscope.exe decode -i "\\Device\\NPF_{...}" --duration 2

On Windows, Npcap interface names are GUID-style device paths, not friendly names like eth0 -- run interfaces first and copy the exact string it prints.

Live decode (-i)

Any subcommand that takes -r also takes -i <interface> instead (mutually exclusive) -- decode, info... wait, info's metadata/histogram view has no live equivalent (there's no natural "end of file" moment for a live interface), but policy validate, inventory, and detect all support -i directly, running their analysis continuously against live traffic instead of a file.

Live decode on loopback, 2-second window

$conduitscope decode -i lo --duration 2
capture on 'lo' stopped (0 packet(s) captured)

-a/--duration, --snaplen, and --no-promiscuous are live-capture-only options -- promiscuous mode is on by default (the main use case is watching a mirrored SPAN/TAP port, which needs traffic not addressed to this host at all).

Packet-loss visibility

Live capture always ends its run with a drop-count line from libpcap/Npcap's own statistics (pcap_stats) -- if the OS dropped packets because this process couldn't keep up, that shows up here, not as silence:

A run with OS-level drops (illustrative)

$conduitscope decode -i eth0 --duration 30
...
capture on 'eth0' stopped (14201 packet(s) captured, 37 packet(s) dropped by the OS -- see USER_GUIDE.md's Packet loss visibility subsection)

capture -- continuous, disk-bounded recording

No decoding, no analysis -- just writes rotated classic-pcap files to a directory, bounded by size/count/time retention policy, meant to run unattended. Analyze the rotated files afterward with decode/inventory/detect/baseline as a separate pass.

Capture on loopback for 2 seconds, rotating at 1 MB, keeping at most 5 files

$conduitscope capture -i lo --duration 2 -d ./rotated --prefix demo --rotate-bytes 1000000 --max-files 5
capturing on 'lo' into './rotated/demo_*.pcap' -- Ctrl+C to stop
0 packet(s) captured across 1 file(s); most recent: './rotated/demo_20261001T151707882654Z_567_000000.pcap' (24 bytes)

Rotation and retention are independent knobs:

OptionControls
--rotate-bytes Nroll to a new file once the current one reaches roughly this many bytes
--rotate-seconds Nroll once a packet's own timestamp is ≥ N seconds past the file's first packet (capture time, not wall clock)
--max-total-bytes Ndelete the oldest rotated file(s) to keep combined size under N (requires a rotation policy above)
--max-files Ndelete the oldest rotated file(s) to keep at most N files total, counting the active one

One tap point (interface) per capture process -- for a multi-tap site, run one independent process per interface, each with its own --directory, then combine their separate analysis passes afterward with merge.

Disk and rotation failure reporting (exit code 7)

If the write side fails mid-capture -- disk full, a permission changed, the target directory disappeared -- capture prints a prominent *** CAPTURE INCOMPLETE *** banner to stderr and exits 7, distinct from exit 1 (never produced any evidence at all). Every already-rotated file up to that point stays intact. See EXIT STATUS for the full table.

BPF filtering on the wire

-f/--filter works the same way for every live-capture-capable subcommand, including capture -- libpcap/Npcap applies it at capture time, before this process even sees non-matching packets:

Capture only Modbus/TCP traffic

$conduitscope capture -i eth0 -f 'tcp port 502' -d ./rotated --rotate-seconds 3600 --max-files 24

Running capture as a long-lived unattended service

systemdsystemd unit (sketch)

# /etc/systemd/system/conduitscope-capture.service
[Unit]
Description=conduitscope continuous capture
After=network.target

[Service]
ExecStart=/usr/local/bin/conduitscope capture -i eth0 -d /var/log/conduitscope/pcap \\
  --prefix eth0 --rotate-seconds 3600 --max-total-bytes 10737418240
Restart=on-failure
User=conduitscope
AmbientCapabilities=CAP_NET_RAW CAP_NET_ADMIN

[Install]
WantedBy=multi-user.target
PowerShellScheduled Task / NSSM (sketch)

# Run from an elevated PowerShell to register a Scheduled Task that starts at boot:
PS>$action = New-ScheduledTaskAction -Execute 'C:\conduitscope\conduitscope.exe' `
>      -Argument 'capture -i "\\Device\\NPF_{...}" -d C:\pcap --prefix eth0 --rotate-seconds 3600'
PS>$trigger = New-ScheduledTaskTrigger -AtStartup
PS>Register-ScheduledTask -TaskName "conduitscope-capture" -Action $action -Trigger $trigger -RunLevel Highest

Either way, capture itself has no daemonization logic (no fork-to-background, no PID file) -- it relies on the OS's own service manager for that, deliberately, so it behaves the same whether launched by systemd, NSSM, a container entrypoint, or just a foreground terminal.
