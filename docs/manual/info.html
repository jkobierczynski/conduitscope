Manual / info -- stats, conversations & Follow Stream

info -- stats, conversations & Follow Stream

info prints pcap file metadata and a protocol histogram without full per-packet output -- a first look at an unfamiliar capture -- plus, when asked with -z/--stat, tshark-style Conversations, Endpoints, and Follow-Stream tables.

You don't need to type "info"

If -z/--stat appears anywhere on the command line, the no-subcommand default becomes info automatically (ROADMAP item 109) -- conduitscope -r FILE -z conv,tcp is exactly conduitscope info -r FILE -z conv,tcp. Every example below types info explicitly for clarity, but either form works.

Default output: metadata and protocol histogram

With no -z at all, info shows the pcap format version, link type, snaplen, timestamp resolution, and a protocol/function-code histogram -- nothing else is tracked unless you ask for it with -z.

info with no -z

$conduitscope info -r tests/sample_modbus.pcap
file:           tests/sample_modbus.pcap
pcap version:   2.4
link type:      Ethernet
snaplen:        262144 bytes
timestamps:     microsecond resolution
packets:        3
time span:      2.002 s
protocols:
  modbus          3
modbus function codes:
  Read Holding Registers                  3
modbus exception responses: 1
modbus responses authoritatively paired (transaction ID, not heuristic): 1
The same, against a real-world capture (79 packets, Siemens S1200 HMI traffic)

$conduitscope info -r tests/real_captures/s7comm/s7comm_1200_hmi.pcap

  cotp            27

Conversations and Endpoints tables (-z)

-z is repeatable -- each occurrence adds one table. Four conversation/endpoint kinds: conv,ip, endpoints,ip, conv,eth, endpoints,eth (Ethernet-layer, by MAC), plus TCP-specific conv,tcp and the Follow-Stream forms below.

-z conv,ip -- IPv4 conversations, ranked by total bytes

$conduitscope info -r tests/sample_inventory.pcap -z conv,ip
ipv4 conversations (5, ranked by total bytes):
  10.0.5.22 <-> 192.168.1.12  4 frame(s), 380 byte(s) total  (A->B: 2 frame(s)/194 byte(s), B->A: 2 frame(s)/186 byte(s), duration 3.003s)
  10.0.5.21 <-> 192.168.1.16  4 frame(s), 312 byte(s) total  (A->B: 2 frame(s)/155 byte(s), B->A: 2 frame(s)/157 byte(s), duration 3.003s)
  10.0.5.21 <-> 192.168.1.11  2 frame(s), 151 byte(s) total  (A->B: 1 frame(s)/72 byte(s), B->A: 1 frame(s)/79 byte(s), duration 1.001s)
  192.168.1.50 <-> 192.168.1.10  2 frame(s), 149 byte(s) total  (A->B: 1 frame(s)/66 byte(s), B->A: 1 frame(s)/83 byte(s), duration 1.001s)
  192.168.1.14 <-> 192.168.1.15  2 frame(s), 124 byte(s) total  (A->B: 1 frame(s)/59 byte(s), B->A: 1 frame(s)/65 byte(s), duration 1.001s)

TCP Follow Stream (-z follow,tcp,stream,N)

Reassembles one TCP stream's payload bytes in each direction and prints them as a hex dump -- Wireshark's "Follow TCP Stream" -- addressed by the same tcp.stream number -z conv,tcp prints.

Follow stream 0

$conduitscope info -r tests/sample_modbus.pcap -z follow,tcp,stream,0
follow tcp stream 0: 192.168.1.50:51000 <-> 192.168.1.10:502
  192.168.1.50:51000 -> 192.168.1.10:502 (1 segment(s), 12 byte(s)):
0000  00 01 00 00 00 06 01 03  00 00 00 0a              ............
  192.168.1.10:502 -> 192.168.1.50:51000 (2 segment(s), 29 byte(s)):
0000  00 01 00 00 00 17 01 03  14 00 00 00 01 00 02 00  ................
0010  03 00 04 00 05 00 06 00  07 00 08 00 09           .............
  (1 out-of-order segment(s) totaling 9 byte(s) never became contiguous -- a gap in this direction's capture, not shown)

A UDP equivalent, follow,udp,stream,N, works the same way for UDP flows (BACnet, CIP I/O, HART-IP, FF-HSE).

Growth caps

Three ceilings, each 0 by default meaning "use the built-in default" (200,000 conversations/endpoints, 16 MiB per Follow-Stream direction): --max-conversations, --max-endpoints, --max-follow-bytes. These exist so an adversarial or pathological capture can't exhaust memory building these tables; see USER_GUIDE.md's own "Conversations and Endpoints tables" subsection for exactly what happens once a cap is hit.
