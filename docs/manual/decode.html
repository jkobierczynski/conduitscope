Manual / decode -- packet-by-packet output

decode -- packet-by-packet output

decode is the base command: read a capture (or live interface), walk each packet, and print whatever it recognizes. Everything else in conduitscope builds on the same decode pass.

Output formats

Five formats, selected with -T/--format: text (default, human- readable), json, csv, fields (print only requested -e values, tab-separated, mirroring tshark -T fields), and zeek (a real Zeek conn.log, one row per TCP/UDP connection, not per packet).

-T texttext (default)

$conduitscope decode -r tests/sample_modbus.pcap
#1  0.000000  192.168.1.50:51000 -> 192.168.1.10:502 (modbus)  [modbus]  Read Holding Registers: request: read 10 holding register(s) starting at address 0
#2  1.001000  192.168.1.10:502 (modbus) -> 192.168.1.50:51000  [modbus]  Read Holding Registers: response: 20 data byte(s) = 00 00 00 01 00 02 00 03 00 04 00 05 00 06 00 07 00 08 00 09
#3  2.002000  192.168.1.10:502 (modbus) -> 192.168.1.50:51000  [modbus]  Read Holding Registers: exception response to Read Holding Registers: Illegal Data Address

Filtering: BPF (-f) vs. display filter (-Y)

Two independent filters, applied at different stages. -f/--filter is a BPF filter (tcpdump syntax), matched against raw bytes before/during decode -- the same filter you'd hand to tcpdump/wireshark -f. -Y/--display-filter is evaluated after decode, against already-dissected fields -- Wireshark's own display-filter language, not BPF. They combine as an intersection when both are given, and a packet that fails -Y doesn't count toward -c/--max-packets.

-f BPFBPF filter -- raw-byte match before decode

$conduitscope decode -r tests/sample_modbus.pcap -f 'tcp port 502' -T fields -e summary
Read Holding Registers: request: read 10 holding register(s) starting at address 0
Read Holding Registers: response: 20 data byte(s) = 00 00 00 01 00 02 00 03 00 04 00 05 00 06 00 07 00 08 00 09
Read Holding Registers: exception response to Read Holding Registers: Illegal Data Address
-YDisplay filter -- decoded-field match, with a quoted string literal

$conduitscope decode -r tests/sample_enip.pcap -Y 'enip.service_name contains "Read"' -T fields -e summary
SendRRData; Read_Tag request path=Pump1_Speed
SendRRData; Read_Tag response: Success
A field's type decides whether it needs quotes

-Y fields are typed (see the full table in USER_GUIDE.md's Display filters section): numeric fields (bacnet.service == 16) and bare dotted-decimal IPv4 literals (ip.src == 10.1.2.3) are written unquoted; string fields need a quoted literal (enip.service_name == "Write_Tag", or contains/matches for substring/regex tests). Comparing a numeric field against a string literal is a compile-time error, not a silent non-match:

Mismatched type -- caught before any packet is read, not silently empty

$conduitscope decode -r tests/sample_detect.pcap -Y 'bacnet.service == "readProperty"'
error: display filter 'bacnet.service == "readProperty"' cannot compare numeric field 'bacnet.service' against a string literal (expected a numeric value, e.g. bacnet.service == 16)

A bare protocol name, with no comparison at all, is a field-existence test across any of the ~115 protocols this tool decodes -- not only the ones in the curated field table:

Bare protocol name as an existence test

$conduitscope decode -r tests/sample_detect.pcap -Y bacnet -T fields -e summary
BVLC Original-Unicast-NPDU Confirmed-Request invoke-id=40 reinitializeDevice
BVLC Original-Unicast-NPDU Confirmed-Request invoke-id=41 deviceCommunicationControl

See JSON output & filtering for how the same quoting problem looks in jq (Linux) and PowerShell (Windows) once the output itself is JSON, rather than a -Y expression on conduitscope's own command line.

Shell quoting for -Y itself

A -Y expression almost always contains spaces, &&, and sometimes embedded double quotes -- all things your shell has its own opinion about before conduitscope ever sees the string.

bashbash/zsh -- single-quote the whole expression

$conduitscope decode -r cap.pcap -Y 'modbus.func_code == 16 && ip.src == 10.1.2.3'

# the expression itself needs a double-quoted string literal (for a string field) --
# single quotes around the whole thing let double quotes through untouched:
$conduitscope decode -r cap.pcap -Y 'enip.service_name contains "Write"'
PowerShellPowerShell -- single-quote the whole expression too

PS>conduitscope decode -r cap.pcap -Y 'modbus.func_code == 16 && ip.src == 10.1.2.3'

# PowerShell single-quoted strings are literal, same idea as bash -- double quotes inside
# pass through untouched:
PS>conduitscope decode -r cap.pcap -Y 'enip.service_name contains "Write"'

# if you must double-quote the OUTER string (e.g. because it's built from a PowerShell
# variable), escape the inner double quotes with a backtick:
PS>$svc = "Write"
PS>conduitscope decode -r cap.pcap -Y "enip.service_name contains `"$svc`""

cmd.exe (not PowerShell) has no single-quote string literal at all -- everything is double-quoted, and an embedded double quote is escaped by doubling it or with a backslash depending on context. This is one of several reasons PowerShell, not cmd.exe, is used for every Windows example in this manual; see JSON & filtering's cmd.exe note if you're stuck scripting from a legacy batch file.

Full layer-by-layer detail (-V)

Mirrors Wireshark's Packet Details pane -- every field -T json would show, grouped by layer, instead of flattened into one summary line. Text output only; composes with -x.

-V -- layer-by-layer breakdown

$conduitscope decode -r tests/sample_modbus.pcap -c 1 -V
#1  Frame: 66 byte(s) captured, 66 byte(s) on wire, 0.000000
Ethernet II: 00:0c:29:11:22:33 -> 00:0c:29:aa:bb:cc
Internet Protocol: 192.168.1.50 -> 192.168.1.10
        ttl: 64
Transmission Control Protocol: 51000 -> 502 (modbus)
        flags: ACK,PSH
        direction: client 192.168.1.50 (port-heuristic)
modbus:
        summary: Read Holding Registers: request: read 10 holding register(s) starting at address 0
        modbus_is_request: true
        modbus_quantity: 10
        modbus_start_address: 0
        note: classified as a request because the PDU is exactly 4 bytes (address+quantity); this is a heuristic, not stream tracking

Selecting packets by position (--range)

Wireshark/editcap-style 1-based packet numbers and ranges -- combines with -f (both must match) and -c (caps how many of the selection are taken).

--range -- same numbering as decode's own #<n> index

$conduitscope decode -r tests/sample_modbus.pcap --range 1-2 -T fields -e summary
Read Holding Registers: request: read 10 holding register(s) starting at address 0
Read Holding Registers: response: 20 data byte(s) = 00 00 00 01 00 02 00 03 00 04 00 05 00 06 00 07 00 08 00 09

Restricting to one protocol (--protocol)

--protocol -- skip auto-detection, decode only this protocol's own dissector

$conduitscope decode -r tests/sample_modbus.pcap --protocol modbus -T fields -e summary

Writing a filtered capture back out (-w)

Writes every packet that reaches the run (after -f, if given) to a new classic-pcap file, raw and unmodified -- mirrors tcpdump/tshark's own -w. Unaffected by -Y, which only governs what's printed. Works identically for -r or -i input.

-w -- save only the packets a BPF filter matched

$conduitscope decode -r tests/sample_modbus.pcap -f 'tcp port 502' -w filtered.pcap
$conduitscope info -r filtered.pcap
file:           filtered.pcap
packets:        3
protocols:
  modbus          3
