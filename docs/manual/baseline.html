Manual / baseline -- learn / check

baseline -- learn / check

ICS communication-baseline analysis at the protocol-operation level (S7comm, Modbus, EtherNet/IP, DNP3, BACnet, OPC UA, MELSEC, FINS, IEC 104): learn what operations and address ranges are normally seen on a conduit from known-good traffic, then check a later capture against that baseline.

Learn

Feed one or more known-good captures; the baseline file accumulates conduits, their operations, and (where that protocol's addressing supports it) the address ranges touched:

Learn from two captures into one baseline file

$conduitscope baseline learn --baseline-file baseline.json tests/sample_modbus.pcap tests/sample_s7comm.pcap
learned from 2 capture(s), touching 2 conduit observation(s); baseline file 'baseline.json' now has 2 conduit(s)
jqWhat a baseline file looks like (one conduit, condensed)

$jq '.conduits[0]' baseline.json
{
  "client_ip": "192.168.1.50",
  "server_ip": "192.168.1.10",
  "protocol": "modbus",
  "server_port": 502,
  "operations": [
    {
      "operation_key": "Read Holding Registers",
      "packet_count": 1,
      "has_target_range": true,
      "observed_ranges": [[0, 10]]
    }
  ]
}

Re-run learn against the same --baseline-file with more captures to extend it incrementally -- operations and ranges are unioned in, never replaced.

Check: clean

A capture that matches everything learned

$conduitscope baseline check --baseline-file baseline.json tests/sample_modbus.pcap
ICS communication-baseline check
  capture: tests/sample_modbus.pcap

Result: CLEAN

1 conduit(s) observed, 1 distinct operation(s) observed, 1 matched the baseline, 0 did not

FINDINGS (0):
  (none)

Check: anomalies found

Two kinds of finding: new-target-range (a known operation touching addresses outside what was learned) and new-operation (an operation never seen at all on this conduit):

A capture with a widened address range and a new operation

$conduitscope baseline check --baseline-file baseline.json tests/sample_baseline_modbus_mutated.pcap
ICS communication-baseline check
  capture: tests/sample_baseline_modbus_mutated.pcap

Result: ANOMALIES FOUND (2 finding(s))

1 conduit(s) observed, 2 distinct operation(s) observed, 0 matched the baseline, 2 did not

FINDINGS (2):
  [1] new-target-range  192.168.1.50 -> 192.168.1.10:502  modbus  operation="Read Holding Registers"  (2 packet(s))
      observed range: [200, 205)
      baseline ranges: [0, 10)
  [2] new-operation  192.168.1.50 -> 192.168.1.10:502  modbus  operation="Write Multiple Registers"  (1 packet(s))
Exit code 4 on any finding

baseline check returns 0 (CLEAN), 4 (ANOMALIES FOUND, both findings and exit code clearly distinguishable from a policy validate violation's own code 3), or 5 (observation truncated -- re-run with a higher --max-baseline-* ceiling, see EXIT STATUS). baseline learn itself always exits 0 -- a possibly-partial baseline is still written, with an INCOMPLETE warning to stderr, not a failure.

SIEM export for check findings

-T cefAnomalies as CEF one-liners

$conduitscope baseline check --baseline-file baseline.json tests/sample_baseline_modbus_mutated.pcap -T cef
CEF:0|conduitscope|conduitscope-baseline|0.2.9|new-target-range|New Target Range|3|src=192.168.1.50 dst=192.168.1.10 dpt=502 proto=modbus cat=new-target-range msg=new-target-range: operation "Read Holding Registers" (observed range 200-205 not fully covered by the baseline) cnt=2
CEF:0|conduitscope|conduitscope-baseline|0.2.9|new-operation|New Operation|5|src=192.168.1.50 dst=192.168.1.10 dpt=502 proto=modbus cat=new-operation msg=new-operation: operation "Write Multiple Registers" cnt=1

-T leef and -T syslog work the same way, matching detect's own SIEM export conventions.

Feeding novelty detection

A learned baseline also feeds detect's own novelty axis (--baseline-file) -- a genuinely new remote-access channel or CIP originator is resolved against the same real history, not just first-occurrence-within-the-capture. See detect -- Novelty against a real baseline.

Which protocols, and at what granularity

S7comm, Modbus, EtherNet/IP, DNP3, BACnet, OPC UA, MELSEC, and FINS all track address ranges per operation where that protocol's own addressing model supports it (Modbus register ranges, DNP3 group/variation/index, EtherNet/IP tag paths, ...); IEC 104 tracks operations without a comparable range concept. See docs/design/baseline-engine.md for the full per- protocol design rationale.
