Manual / JSON output & filtering (jq / PowerShell)

JSON output & filtering

Every report-producing subcommand supports -T json (decode also supports csv/fields/zeek; several others add cef/leef/syslog -- see each subcommand's own page). This page is a dedicated set of recipes for piping that JSON into something that filters it: jq on Linux/macOS, and PowerShell's native JSON cmdlets (or jq again, with a caveat) on Windows -- with the shell-quoting differences called out explicitly, since that's where most copy-pasted commands actually break.

Every example below was actually run

Against tests/sample_modbus.pcap, tests/sample_inventory.pcap, tests/sample_enip.pcap, and tests/sample_detect.pcap with jq 1.7 on Linux -- and every jq example's own output on this page has just been re-verified against the current binary (two had gone stale after fixtures grew: the protocol histogram below was missing a cotp entry, and the Critical-findings list was missing two BACnet findings -- both fixed). The PowerShell column was originally written as the idiomatic native-cmdlet equivalent for each, without being run against a real Windows shell. A reader actually running several of these on real Windows PowerShell (thank you) turned up a genuine pipeline-chaining pitfall, confirmed twice independently (once with Group-Object, once with Select-Object | ConvertTo-Csv): chaining anything directly onto ConvertFrom-Json's output in one pipeline statement reading from a native command is unreliable on Windows PowerShell -- it can silently come back empty or collapsed to one item. Every PowerShell example on this page now saves ConvertFrom-Json's output to a variable first and operates on that, which was confirmed working in both cases where the direct-chain form broke -- see each section's own note for specifics. Where a PowerShell-specific quoting quirk is involved (the jq-on-Windows section below), it's called out as such.

The baseline: pretty-printing

bash + jqjq '.' pretty-prints; jq is also the simplest way to check output is valid JSON at all

$conduitscope decode -r tests/sample_modbus.pcap -T json | jq '.'
[
  {
    "index": 1,
    "src_ip": "192.168.1.50",
    "dst_ip": "192.168.1.10",
    "summary": "Read Holding Registers: request: read 10 holding register(s) starting at address 0",
    ...
  },
  ...
]
PowerShellConvertFrom-Json / ConvertTo-Json needs no extra install -- it ships with PowerShell

PS>$report = .\conduitscope decode -r tests\sample_modbus.pcap -T json | ConvertFrom-Json
PS>$report | ConvertTo-Json -Depth 10
[
  {
    "index":  1,
    "src_ip":  "192.168.1.50",
    "dst_ip":  "192.168.1.10",
    "summary":  "Read Holding Registers: request: read 10 holding register(s) starting at address 0",
    ...
  },
  ...
]

-Depth 10 matters: ConvertTo-Json's default depth is only 2, which silently flattens nested objects (e.g. detect's summary object, or inventory's assets array of objects with their own nested fields) into "System.Object[]" placeholders instead of real JSON. Always pass an explicit -Depth generous enough for the report you're formatting.

Select rows by a field value

bash + jqjq select() -- single quotes around the whole filter let the double-quoted jq string literal through untouched

$conduitscope decode -r tests/sample_inventory.pcap -T json | jq -c '.[] | select(.protocol == "modbus") | {src: .src_ip, dst: .dst_ip, summary}'
{"src":"192.168.1.50","dst":"192.168.1.10","summary":"Read Holding Registers: request: read 10 holding register(s) starting at address 0"}
{"src":"192.168.1.10","dst":"192.168.1.50","summary":"Read Holding Registers: response: 20 data byte(s) = 00 00 00 01 00 02 00 03 00 04 00 05 00 06 00 07 00 08 00 09"}
PowerShellWhere-Object + Select-Object with a calculated property for renaming -- save to a variable first

PS>$report = .\conduitscope decode -r tests\sample_inventory.pcap -T json | ConvertFrom-Json
PS>$report | Where-Object { $_.protocol -eq "modbus" } |
>      Select-Object @{n="src"; e={$_.src_ip}}, @{n="dst"; e={$_.dst_ip}}, summary

src           dst            summary
---           ---            -------
192.168.1.50  192.168.1.10   Read Holding Registers: request: read 10 holding register(s)...
192.168.1.10  192.168.1.50   Read Holding Registers: response: 20 data byte(s) = 00 00 00...

Count / group by a field

bash + jqgroup_by + map -- a one-liner protocol histogram, same data info's own built-in histogram shows, built by hand

$conduitscope decode -r tests/sample_inventory.pcap -T json | jq '[.[] | .protocol] | group_by(.) | map({protocol: .[0], count: length})'
[
  {
    "protocol": "bacnet",
    "count": 2
  },
  {
    "protocol": "cotp",
    "count": 2
  },
  {
    "protocol": "dnp3",
    "count": 2
  },
  {
    "protocol": "enip",
    "count": 4
  },
  {
    "protocol": "modbus",
    "count": 2
  },
  {
    "protocol": "s7comm",
    "count": 2
  }
]
PowerShellGroup-Object does this natively, no manual grouping logic needed -- save to a variable first

PS>$report = .\conduitscope decode -r tests\sample_inventory.pcap -T json | ConvertFrom-Json
PS>$report | Group-Object protocol | Select-Object Name, Count

Name     Count
----     -----
modbus   2
dnp3     2
cotp     2
s7comm   2
enip     4
bacnet   2

Save to $report first, then pipe that into Group-Object -- don't chain anything directly onto ConvertFrom-Json in the same pipeline that's reading a native command's output. Confirmed on real Windows PowerShell: a single-statement conduitscope ... | ConvertFrom-Json | Group-Object protocol | Select-Object Name, Count reliably came back with exactly one group (a blank name, count 1) instead of the six shown above, while assigning the parsed array to a variable first and then grouping that worked correctly every time. This isn't specific to Group-Object -- the same thing happened with Select-Object | ConvertTo-Csv chained directly (see the "Flatten to CSV" section below), so every PowerShell example on this page now saves to a variable first as a general rule, not just this one. (Group-Object's own row order here is first-seen order in the input, not alphabetical -- that's why it doesn't match the jq histogram's alphabetical order above.)

Flatten to CSV

bash + jqjq -r with @csv -- raw output, no surrounding JSON string quotes

$conduitscope decode -r tests/sample_modbus.pcap -T json | jq -r '.[] | [.src_ip, .dst_ip, .summary] | @csv'
"192.168.1.50","192.168.1.10","Read Holding Registers: request: read 10 holding register(s) starting at address 0"
"192.168.1.10","192.168.1.50","Read Holding Registers: response: 20 data byte(s) = 00 00 00 01 00 02 00 03 00 04 00 05 00 06 00 07 00 08 00 09"
"192.168.1.10","192.168.1.50","Read Holding Registers: exception response to Read Holding Registers: Illegal Data Address"

Or skip -T json | jq entirely -- decode has a real -T csv of its own (more columns, RFC4180-quoted) -- see decode's own CSV example. jq is worth it here mainly when you want a different column set than the built-in CSV gives you.

PowerShellConvertTo-Csv -- same idea, PowerShell's own object pipeline does the quoting -- save to a variable first

PS>$report = .\conduitscope decode -r tests\sample_modbus.pcap -T json | ConvertFrom-Json
PS>$report | Select-Object src_ip, dst_ip, summary | ConvertTo-Csv -NoTypeInformation

"src_ip","dst_ip","summary"
"192.168.1.50","192.168.1.10","Read Holding Registers: request: read 10 holding register(s) starting at address 0"
"192.168.1.10","192.168.1.50","Read Holding Registers: response: 20 data byte(s) = 00 00 00 01 00 02 00 03 00 04 00 05 00 06 00 07 00 08 00 09"
"192.168.1.10","192.168.1.50","Read Holding Registers: exception response to Read Holding Registers: Illegal Data Address"

Confirmed broken on real Windows PowerShell when chained directly (no intermediate variable): .\conduitscope ... | ConvertFrom-Json | Select-Object src_ip, dst_ip, summary | ConvertTo-Csv ... came back with the header row and zero data rows. Saving to $report first and piping that fixed it -- see the note in the "Count / group by a field" section above for the same pitfall with Group-Object. Given it reproduces with two different downstream cmdlets now, treat it as a general rule for this page, not a Group-Object-specific one: always save ConvertFrom-Json's output to a variable before piping it into anything else.

{"technique_id":"T0855","description":"BACnet DeviceCommunicationControl request -- a device's own communication can be silenced or re-enabled by this service"}
bash + jqFindings per category, counted

$conduitscope detect -r tests/sample_detect.pcap -T json | jq '.findings | group_by(.category) | map({category: .[0].category, count: length})'
[
  { "category": "Firmware/Logic Change", "count": 4 },

PS>$report = .\conduitscope detect -r tests\sample_detect.pcap -T json | ConvertFrom-Json
PS>$report.findings | Where-Object { $_.severity -eq "Critical" } | Select-Object technique_id, description
PowerShellFindings per category, counted

PS>$report.findings | Group-Object category | Select-Object Name, Count

Remote-Access Channel    1

Saving the parsed report to a variable first ($report = ... | ConvertFrom-Json) and querying it with several separate commands avoids re-running conduitscope and re-parsing JSON for every question -- worth doing as soon as you're asking more than one.

Sort by a field

bash + jqsort_by -- jq sorts ascending, so negate the field for descending

$conduitscope decode -r tests/sample_bacnet.pcap -T json | jq -c '[.[] | {index, captured_len}] | sort_by(-.captured_len) | .[0:3]'
[{"index":53,"captured_len":143},{"index":54,"captured_len":94},{"index":66,"captured_len":85}]
PowerShellSort-Object -Descending, then take the top 3 -- save to a variable first

PS>$report = .\conduitscope decode -r tests\sample_bacnet.pcap -T json | ConvertFrom-Json
PS>$report | Sort-Object captured_len -Descending | Select-Object -First 3 index, captured_len | ConvertTo-Json

[
  {
    "index":  53,
    "captured_len":  143
  },
  {
    "index":  54,
    "captured_len":  94
  },
  {
    "index":  66,
    "captured_len":  85
  }
]

Piping the final result through ConvertTo-Json instead of letting it print as a default table isn't required -- it's done throughout this page's newer examples specifically because ConvertTo-Json's output format is stable and well-documented, whereas a bare Format-Table's exact column widths depend on console width and aren't worth guessing at without a real Windows shell to check against.

Min, max, and average of a numeric field

bash + jqmin / max / add-over-length for the average, all in one object construction

$conduitscope decode -r tests/sample_bacnet.pcap -T json | jq '[.[].captured_len] | {min: min, max: max, avg: (add/length)}'
{
  "min": 44,
  "max": 143,
  "avg": 60.4264705882353
}
PowerShellMeasure-Object does min/max/average natively

PS>$report = .\conduitscope decode -r tests\sample_bacnet.pcap -T json | ConvertFrom-Json
PS>$stats = $report.captured_len | Measure-Object -Minimum -Maximum -Average
PS>[PSCustomObject]@{ min = $stats.Minimum; max = $stats.Maximum; avg = [math]::Round($stats.Average, 2) } | ConvertTo-Json

{
  "min":  44,
  "max":  143,
  "avg":  60.43
}

The average is rounded to 2 decimal places with [math]::Round(...) here rather than shown at jq's full floating-point precision -- .NET's and jq's default number-to-string formatting don't necessarily agree on every trailing digit of a repeating decimal, so rounding sidesteps a mismatch that's cosmetic, not a real difference in the underlying value (both are computing the same 4109 ÷ 68).

Distinct / unique values

bash + jqunique -- note this sorts the result, it doesn't just dedupe in place

$conduitscope decode -r tests/sample_bacnet.pcap -T json | jq -c '[.[].src_ip] | unique'
["192.168.1.10","192.168.1.20","192.168.1.21"]
PowerShellSelect-Object -Unique -- preserves first-seen order instead of sorting

PS>$report = .\conduitscope decode -r tests\sample_bacnet.pcap -T json | ConvertFrom-Json
PS>$report | Select-Object -ExpandProperty src_ip -Unique | ConvertTo-Json

[
  "192.168.1.10",
  "192.168.1.20",
  "192.168.1.21"
]

Same three addresses here either way, but don't count on that in general: jq's unique always sorts, while PowerShell's -Unique keeps whatever order the values first appeared in the capture.

$conduitscope decode -r tests/sample_dnp3.pcap -T json | jq -c '.[] | select((.time | tonumber) >= 10 and (.time | tonumber) <= 15) | {index, time}'

Escape characters: when the data itself contains a quote

Every example so far sidestepped the hard case: a filter value that itself contains the same quote character your shell or your filter language is using as a delimiter. conduitscope's own output genuinely has one -- sample_enip.pcap's ListIdentity response summary embeds a quoted device name:

The real field value

$conduitscope decode -r tests/sample_enip.pcap -T json | jq -r '.[3].summary'
ListIdentity; identity: vendor=1 device_type=12 product_code=54 rev=2.1 serial=0x1337ab name="Conduit-ENIP-Sample"

Matching on text that includes name="Conduit means the double quote has to survive three layers: your shell's own quoting, jq's own string-literal syntax, and (if applicable) a further layer if that command is itself inside a script.

bash + jqbash: outer single quotes, inner double quote backslash-escaped inside jq's own string

$conduitscope decode -r tests/sample_enip.pcap -T json |
>    jq -c '.[] | select(.summary | contains("name=\"Conduit")) | .summary'
"ListIdentity; identity: vendor=1 device_type=12 product_code=54 rev=2.1 serial=0x1337ab name=\"Conduit-ENIP-Sample\""

# the shell sees ONE single-quoted argument (so it never touches the embedded " chars);
# jq then parses contains("name=\"Conduit") as its own double-quoted string containing an
# escaped double quote -- two separate escaping layers, only the inner one is jq's
bash's own single-quote escape, for when the SHELL quote itself is the one you need inside

Separately from the jq example above: if you ever need a literal single quote inside a single-quoted bash argument (not needed for the jq case above, but a common follow-up question), bash has no escape character inside single quotes at all -- the idiom is to close the quote, insert an escaped or double-quoted single quote, and reopen: 'can'\''t' (close after can, \' is one escaped single quote outside any quoting, then reopen with 't') produces the literal text can't.

PowerShellPowerShell: -like avoids the nested-quote problem entirely (recommended) -- save to a variable first

PS>$report = .\conduitscope decode -r tests\sample_enip.pcap -T json | ConvertFrom-Json
PS>$report | Where-Object { $_.summary -like '*name="Conduit*' } | Select-Object -ExpandProperty summary

ListIdentity; identity: vendor=1 device_type=12 product_code=54 rev=2.1 serial=0x1337ab name="Conduit-ENIP-Sample"

# PowerShell single-quoted strings are literal -- the embedded " needs no escaping at all here,
# because -like's own wildcard string never has to be re-parsed by a second language the way
# a jq filter string does.

This is the strongest practical argument for the native-cmdlet approach on Windows over piping to jq.exe: PowerShell's own argument-passing to a native executable (as opposed to a PowerShell cmdlet) re-quotes the string for the Win32 process-creation API, and a double quote inside a single-quoted PowerShell string survives that trip -- but a filter that itself needs internal double-quote escaping (like the bash jq example on the left) does not translate directly; see the callout below.

jq on Windows: a known quoting pitfall

jq itself works fine on Windows (winget install jqlang.jq or choco install jq), and most single-double-quote filters (jq '.[] | select(.protocol == "modbus")') work unchanged from PowerShell, since PowerShell's single-quoted strings pass through to a native executable's argv mostly intact. The pitfall is specifically a filter that needs an escaped double quote inside its own double-quoted jq string (the contains("name=\"Conduit") case above) -- PowerShell's own re-quoting for native-executable arguments and jq's internal argument parsing can disagree about which backslash-escaped characters survive the trip, and the exact behavior has changed across PowerShell versions. If a jq filter with an internal escaped quote doesn't behave as expected on Windows, reach first for the native ConvertFrom-Json / Where-Object approach shown throughout this page instead of debugging the quoting -- it sidesteps the problem rather than working around it.

A note on cmd.exe

Every Windows example on this site uses PowerShell, not cmd.exe (the classic C:\> prompt / .bat files). cmd.exe has no single-quote string literal at all -- every argument is double-quoted, and an embedded double quote is escaped by doubling it ("") in some contexts and by a backslash in others, inconsistently, depending on whether the receiving program uses the standard Win32 CommandLineToArgvW parsing rules. This makes any filter with embedded quotes (the -Y and jq examples throughout this manual) substantially harder to write correctly in cmd.exe than in PowerShell, with no equivalent to PowerShell's own literal single-quoted string. If you're scripting conduitscope from an existing .bat file, the most reliable fix is usually to call powershell.exe -File script.ps1 ... from the batch file and do the actual filtering in a real .ps1 script, rather than fighting cmd.exe's own quoting rules directly.

Streaming large output: don't buffer the whole report first

For a capture large enough that building the whole JSON array in memory first is wasteful, prefer -T fields (tab-separated, one line per packet, streams naturally -- see decode's own -T fields example) over -T json | jq for simple per-packet filtering; reach for JSON+jq/PowerShell specifically when you need jq's/PowerShell's own aggregation (group_by/Group-Object, nested-object reshaping) that -T fields can't express.
