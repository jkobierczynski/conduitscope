Manual / evidence -- audit evidence packs

evidence -- audit evidence packs

One command that assembles an audit-binder-ready report: the observed zone/conduit topology (reuses inventory), policy compliance mapped to IEC 62443 FR5 / NIS2 (reuses policy validate, if --policy is given), detection findings with their own FR mapping (reuses detect), an optional baseline check (reuses baseline check, if --baseline-file is given), an optional NERC CIP-007 R4-style monitoring-coverage note, and a reproducible integrity record (tool version, SHA-256 hashes, an optional HMAC-SHA256 signature).

Not a compliance determination

Every framework mapping below (FR5/SL-T, NIS2, CIP) is this tool's own interpretive cross- reference, never an official conformance or compliance determination -- a qualified assessor's own judgment is still required. The report says this itself, verbatim, in its own SCOPE & HONESTY NOTE section (reproduced in the first example below) -- it is not manual-only framing.

Full-feature run

Add a baseline check, an operator-declared Security Level target (echoed verbatim, never computed from traffic -- IEC 62443-3-2 defines SL-T as an organizational risk-assessment output), the NERC CIP-007 R4 monitoring-coverage note, and an HMAC-signed integrity stamp:

Every optional section turned on

$conduitscope evidence -r tests/sample_detect.pcap \\
>    --policy tests/policies/compliant.yaml \\
>    --baseline-file baseline.json \\
>    --sl-target SL2 \\
>    --cip-monitoring-window \\
>    --sign-key hmac.key \\
>    -o evidence_pack.txt

The Integrity section then includes a hex HMAC-SHA256 signature plus a one-line recipe to independently verify it offline -- the report is meant to leave the conduitscope installation entirely and still be checkable.

Exit codes

evidence reuses the same exit-code vocabulary as the subcommands it wraps, combined onto one report: 0 (clean), 3 (policy non-compliant, if --policy given), 4 (baseline anomalies, if --baseline-file given), 1 (a required input couldn't be read), and 6 (any wrapped engine's own observation was truncated -- takes priority over every other code, including 0/3/4). See EXIT STATUS for the exact precedence rules.

When to reach for this vs. the individual subcommands

Run the individual subcommands (inventory, policy validate, detect, baseline check) directly while you're actively investigating -- their own JSON/CEF/CSV exports are better suited to scripting and SIEM pipelines. Reach for evidence once, at the end, to produce the single document that goes in the audit binder or gets attached to a compliance ticket.
