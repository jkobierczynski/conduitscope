Manual / inventory -- passive asset discovery

inventory -- passive asset discovery

Infers a first-draft asset list, communications matrix, and zone/conduit model from a capture -- the opposite direction from policy validate , which checks traffic against a policy you already wrote. Run inventory first on an unfamiliar network; feed its output into policy validate once you've reviewed it.

Asset-only exports: CSV and STIX 2.1

-T csv and -T stix are both deliberately asset-only (one row/object per device) -- for CMDB import or threat-intel tooling. Use text/json for the full communications/zones/conduits picture.

Topology diagram (--diagram)

A Mermaid or Graphviz/DOT zone-communication graph, written to a file -- render it with any Mermaid-compatible viewer (e.g. mermaid.live) or dot.

Inferred zone/conduit policy (--policy-out)

Writes a ready-to-edit YAML policy file in exactly the schema policy validate expects -- zones grouped by observed /24 subnet, one conduit per distinct (zone-pair, protocol, port) combination actually seen:

--policy-out inferred.yaml

$conduitscope inventory -r tests/sample_inventory.pcap --policy-out inferred.yaml
$cat inferred.yaml
# Auto-generated by `conduitscope inventory` -- a FIRST-DRAFT zone/conduit policy inferred from
# observed traffic, not a hand-authored security policy. Review it ... before using it to
# gate real `policy validate` runs.
zones:
  zone_10_0_5_0_24:
    description: "Inferred from observed traffic: 2 asset(s) in 10.0.5.0/24"
    networks:
      - 10.0.5.0/24
  zone_192_168_1_0_24:
    description: "Inferred from observed traffic: 7 asset(s) in 192.168.1.0/24"
    networks:
      - 192.168.1.0/24

conduits:
  - name: "zone_10_0_5_0_24 -> zone_192_168_1_0_24 (dnp3/20000)"
    from: zone_10_0_5_0_24
    to: zone_192_168_1_0_24
    protocols: [dnp3]
    ports: [20000]
  ...
Review before enforcing

An inferred policy reflects what the capture happened to contain, not what segmentation was intended -- a capture that's too short, or taken at the wrong tap point, produces a policy that's too permissive. Read it before wiring it into a gating policy validate run; see policy validate's own round-trip example.

Firewall/ACL export

--acl-out FILE --acl-format {cisco,fortinet,paloalto} renders the same inferred conduits as vendor-flavored ACL syntax -- a starting point for an actual firewall rule set, with the same review caveat as the policy export above.

Cisco-flavored ACL sketch

$conduitscope inventory -r tests/sample_inventory.pcap --acl-out rules.txt --acl-format cisco

Edges/conduits as CSV

--edges-csv and --conduits-csv export the raw communication edges and the derived conduit list as flat CSV, for spreadsheet review or import elsewhere -- useful alongside -T csv's asset-only view when you want the relationships too.

Edges and conduits as CSV

$conduitscope inventory -r tests/sample_inventory.pcap --edges-csv edges.csv --conduits-csv conduits.csv
