Manual / detect -- OT incident-response findings

detect -- OT incident-response findings

Flags the things an OT incident-response team actually recognizes: engineering- station mode changes, firmware/logic downloads and restarts, protocol misuse, and new remote-access channels. Every finding cites a MITRE ATT&CK for ICS technique and never asserts malicious intent -- the judgment belongs to the human analyst reading the report.

The four-axis model

Every finding carries three independent, explicitly labeled dimensions, plus a protocol/ category description that is itself a fourth, non-independent axis:

AxisValuesMeans
evidenceConfirmed / Heuristichow reliably the event was observed -- read directly off the wire vs. partly inferred
noveltyConfirmed New / First Occurrence / N/Anew vs. known (against a --baseline-file if given, otherwise first-seen-in-this-capture)
severityCritical / Moderate / Informationalimpact if the finding is genuine
category / techniquee.g. Firmware/Logic Change / T0843what happened and its MITRE ATT&CK for ICS technique ID

These three axes are deliberately kept separate rather than collapsed into one score -- a Heuristic-evidence finding is never silently promoted to Confirmed, and novelty never changes severity, in any output format. See DEVELOPMENT.md's ROADMAP item 119 for the regression suite that specifically proves this invariant holds across every export format below.

SIEM export: CEF / LEEF / syslog

-T cef/-T leef/-T syslog render one curated line per finding, with evidence and novelty carried as labeled custom fields (cs1/ cs1Label, cs2/cs2Label) rather than folded into the severity number -- so a SIEM operator filtering on cs1=Heuristic can still see the real CEF/LEEF severity independently.

-T cefCEF -- severity (the number after the technique name) maps from Critical/Moderate/Informational

$conduitscope detect -r tests/sample_detect.pcap -T cef

Forward any of these straight to a log pipeline:

Stream CEF findings to a syslog collector

$conduitscope detect -r tests/sample_detect.pcap -T cef | logger -n siem.internal -P 514 -T

Novelty against a real baseline

Without --baseline-file, "new vs. known" means first-occurrence-within-this- capture. With it, novelty is resolved against real history from baseline learn -- a conduit already in the baseline isn't flagged at all; one genuinely absent gets Confirmed New:

Same capture, now checked against a learned baseline

$conduitscope baseline learn --baseline-file known.json tests/sample_modbus.pcap tests/sample_s7comm.pcap
$conduitscope detect -r tests/sample_detect.pcap --baseline-file known.json -T json | jq '.findings[] | select(.novelty == "Confirmed New")'

Resource bounds

detect tracks internal state (flow history, per-conduit novelty tables) bounded by several --max-detect-* ceilings -- hitting one doesn't fail the run, but marks the report OBSERVATION INCOMPLETE and returns exit code 6 rather than silently under-reporting. See EXIT STATUS code 6, and DEVELOPMENT.md's ROADMAP item 118 for the clean-vs-degraded distinction this manual's own CI fix (ROADMAP item 120) added regression coverage for.
