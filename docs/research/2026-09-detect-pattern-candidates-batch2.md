# Further `detect` pattern candidates -- batch of 18 (3x6), sourced from real Snort/Suricata OT rulesets and public ICS advisories

## Who asked, why

Jurgen asked directly: "create a list of a batch of 3 times 6 further additional patterns from real Snort/Suricata OT rulesets and public ICS advisories to add to the detection" -- a direct follow-up to Grok review item 4's `detect` subcommand and its existing "Snort-style pattern extensions" (item 89 in `docs/DEVELOPMENT.md`'s ROADMAP -- CIP Identity Object write, DNP3 Operate-without-Select, Modbus write-outside-every-range-read, BACnet Who-Is flood, S7comm Setup Communication probing, and the download-then-restart composite). This is a **candidate list for review, not yet implemented** -- every item below is sourced from a real, cited, independently-verified public ruleset or advisory (never invented or assumed from training data, per this project's own standing rule), and cross-checked against conduitscope's actual decoded fields (`include/conduitscope/*.hpp`) to note what's already wireable today versus what would need new decode work first.

## How to read each entry

Each item gives: the **source** (real SID/CVE/advisory, with URL), the **wire-level condition**, the **conduitscope mapping** (finding category, suggested MITRE ATT&CK-for-ICS technique, evidence/severity/novelty posture consistent with the existing four-axis model), and a **readiness** note (whether the field is already decoded, so this is pure `detect_engine.cpp` wiring, or whether it needs new decode work first).

## Batch 1 -- Modbus/TCP control-plane and reconnaissance operations (Quickdraw-Snort `modbus.rules`)

All six of these come from Digital Bond's `modbus.rules` (SIDs 1111001-1111011); none of these function codes/sub-functions are currently wired into `DetectEngine`, though `modbus.hpp` already decodes function codes generically.

1. **Force Listen Only Mode** -- SID 1111001, `"SCADA_IDS: Modbus TCP - Force Listen Only Mode"`. Wire condition: function code `0x08` (Diagnostics) with sub-function `0x0004`. Puts the slave into a silent, non-responding diagnostic mode -- an engineering-station-only operation with no legitimate reason to appear outside a maintenance window. Mapping: `EngineeringStationActivity`, **T0858** (Change Operating Mode), evidence Confirmed, severity Critical, novelty N/A (always-notable, same posture as S7 PLC Stop). Readiness: needs the Diagnostics sub-function field exposed on the decoded Modbus struct (currently only the top-level function code is tracked per the struct definition read this session) -- small decode addition, not a new decoder.
2. **Restart Communications Option** -- SID 1111002, function code `0x08` sub-function `0x0001`. Forces the slave to reinitialize its comm layer and clear its event log. Mapping: `FirmwareLogicChange`/`EngineeringStationActivity`, **T0816** (Device Restart/Shutdown), Critical, N/A -- same treatment this codebase already gives DNP3 Cold/Warm Restart and UMAS START_PLC/STOP_PLC. Readiness: same sub-function exposure as #1.
3. **Clear Counters and Diagnostic Registers** -- SID 1111003, function code `0x08` sub-function `0x000A`. Wipes exactly the diagnostic counters an investigator would use to establish how long an issue has been present -- an anti-forensic-shaped action distinct from a restart. Mapping: this is the one item in this batch that does **not** cleanly fit the existing 10-entry MITRE table -- **T0872** (Indicator Removal on Host, verified directly at `attack.mitre.org/techniques/T0872/` this session) is the correct fit and would need to be added to `mitre_attack_ics.hpp`. Severity Moderate (state tampering, not control manipulation), evidence Confirmed, novelty N/A. Readiness: same sub-function exposure as #1/#2, plus one new `mitre_attack_ics.hpp` entry.
4. **Read Device Identification** -- SID 1111004, function code `0x2B` (43) with MEI type `0x0E`. Reconnaissance: pulls vendor name/product code/firmware revision off the device. Mapping: `EngineeringStationActivity`, **T0888** (Remote System Information Discovery), evidence Confirmed, novelty resolved the same new-vs-known way the existing CIP/UMAS engineering-station-originator finding already is (`--baseline-file` or first-occurrence). Readiness: `0x2B` is already a recognized function code per the Quickdraw rule's own match; confirm conduitscope's `modbus.cpp` already names it (it decodes function codes generically already) before wiring -- likely a pure `detect_engine.cpp` addition.
5. **Report Server ID** -- SID 1111005, function code `0x11` (17). Same reconnaissance shape as #4, an older/simpler device-info query. Mapping: identical to #4 -- `EngineeringStationActivity`, **T0888**, new-vs-known novelty. Readiness: same as #4.
6. **Repeated exception-code response burst** -- generalizes Quickdraw SIDs 1111010 (`"Slave Device Busy Exception Code Delay"`, exception code `0x06`) and 1111011 (`"Acknowledge Exception Code Delay"`, exception code `0x05`), both `threshold: count 3-5, seconds 60`. Wire condition: the *same server* returns the *same* Modbus exception code 3+ times within roughly a minute. A real, if weak, probing/instability signal -- an engineering tool or a scanner repeatedly hitting a function the device can't currently service. Mapping: `ProtocolMisuse`, **T0855** (Unauthorized Command Message), evidence Confirmed, severity Moderate (deliberately weaker, same posture as the existing Modbus-write-without-prior-read pattern -- legitimate retry logic can trigger this too). Readiness: needs per-(client,server) exception-code counting in `detect_engine.cpp`'s `finish()` pass, mirroring the BACnet Who-Is-flood counter already built.

## Batch 2 -- DNP3 control-plane operations and known scanner-tool fingerprints (Quickdraw-Snort `dnp3.rules` + CyberICS `scada-scan.rules` + nmap's own NSE source)

7. **DNP3 Stop Application** -- SID 1111209, `"SCADA_IDS: DNP3 - Stop Application"`, function code `0x12`. Distinct from the already-implemented Cold/Warm Restart (`0x0D`/`0x0E`) -- this halts the outstation's application layer without a full restart. Mapping: `EngineeringStationActivity`, **T0858** (Change Operating Mode), Critical, N/A -- a genuinely new always-notable DNP3 source, same tier as the existing Cold/Warm Restart findings. Readiness: `dnp3.cpp` already names function codes per the existing design (Cold/Warm Restart, Enable/Disable Unsolicited are already wired); confirm `0x12` is already named, then this is pure `detect_engine.cpp` wiring.
8. **DNP3 broadcast request** -- SIDs 1111211/1111212, `"Broadcast Request from Authorized/Unauthorized Client"`, destination address `0xFFFF` (DNP3's own reserved broadcast address; `0xFFFD`/`0xFFFE` are the confirmed/unconfirmed broadcast variants in the DNP3 spec). A write/operate command sent to the broadcast address reaches every outstation on the segment at once -- a single message with plant-wide blast radius, worth flagging distinctly from an ordinary point-to-point Operate. Mapping: `ProtocolMisuse`, **T0855**, evidence Confirmed, severity Critical given the blast radius, novelty N/A. Readiness: needs the destination-address field checked against the three reserved broadcast values in `detect_engine.cpp` -- the field itself is already decoded (DNP3 addressing is already tracked for conduit identification).
9. **DNP3 function-code / points-list enumeration sweep** -- generalizes SIDs 1111213/1111214 (`"Points List Scan"`/`"Function Code Scan"`, both response-side, `threshold: count 3-5, seconds 30-60` on exception/error responses `0x81`). Wire condition, adapted to conduitscope's own request-side visibility: a single master issuing reads across an unusually wide spread of distinct object groups/variations against one outstation within a short window -- an engineering-tool-shaped enumeration sweep. Mapping: `EngineeringStationActivity`, **T0888**/**T0861** (Point & Tag Identification), evidence Confirmed, novelty N/A (the sweep shape itself is notable regardless of who's doing it), severity Moderate. Readiness: same mechanism as the already-built BACnet Who-Is-flood counter, adapted to DNP3 object-group diversity per source.
10. **Known Modbus scanner-tool fingerprint (Metasploit)** -- CyberICS SID 101563260, `"CYBER-SEC-ICS POLICY SCADA-SCAN Modbus detect like msfconsole"`, exact byte match `|21 00 00 00 00 06 01 04 00 01 00 00|` on TCP/502 (Metasploit's `scada/modbus_findunitid`/`modbus_detect` auxiliary modules' own fixed Read Holding Registers probe framing). Distinguishes an automated scanner's byte-exact, tool-generated request from a legitimate engineering client's Read Holding Registers call (which conduitscope already decodes but doesn't currently distinguish by tool fingerprint). Mapping: `ProtocolMisuse`, **T0888**, evidence Confirmed (byte-exact match), severity Informational-to-Moderate (a scan, not damage). Readiness: pure byte-pattern match in `detect_engine.cpp`, no new decode work -- the whole Modbus TCP payload is already available to compare against.
11. **Known Modbus scanner-tool fingerprint (nmap)** -- CyberICS SIDs 101563263/101563264 (`"Modbus scan looking like nmap"`, content `|00 00 00 00 00 02 01 11|` and `|00 00 00 00 00 05 01 2b 0e 01 00|`), independently cross-checked against nmap's own published `modbus-discover.nse` source. These are nmap's fixed-byte Report Server ID (`0x11`) and Read Device Identification (`0x2B`/MEI `0x0E`) probe framings -- the *same function codes* as batch-1 items #4/#5, but a **tool-specific fingerprint** worth its own distinct, higher-confidence finding rather than folding into the generic reconnaissance finding. Mapping: `ProtocolMisuse`, **T0888**, evidence Confirmed, severity Informational. Readiness: same as #10, pure byte-pattern match.
12. **Known BACnet scanner-tool fingerprint (nmap)** -- CyberICS SIDs 101563265-101563272 (BACnet UDP/47808 Who-Is/ReadProperty object-property sweep rules "looking like nmap"). A tool-specific variant of the already-implemented generic BACnet Who-Is-flood threshold (item 89) -- this would either refine that existing detector with a "known-tool shape" sub-classification, or ship as its own distinct finding when the exact nmap BACnet NSE byte framing is confirmed. Mapping: `ProtocolMisuse`, **T0888**, evidence Confirmed, severity Informational. Readiness: needs the specific nmap BACnet NSE script's own request bytes read directly (not yet done this session -- the CyberICS repo's rule *content* for this section wasn't fetched, only its rule *count and target*) before implementing; flagged here as the one item in this batch needing one more research pass before it's implementation-ready.

## Batch 3 -- Public CVE/advisory-grounded protocol-field anomalies and cross-protocol weak-security/recon patterns

13. **Modbus MBAP declared-length anomaly** -- grounded in **CVE-2017-16740** (NVD; a real, published buffer-overflow vulnerability in Rockwell Allen-Bradley MicroLogix triggered by a crafted Modbus/TCP MBAP header length field). conduitscope's own `modbus.hpp` already decodes `mbap_length` (confirmed by reading the struct this session) and already has a documented, tested maximum (254, per the struct's own comment: "mbap_length can never legitimately exceed 254"). Mapping: flag an `mbap_length` that is internally inconsistent with the actual received payload size, or that sits at/above that documented ceiling from a client. `ProtocolMisuse`, **T0855**, evidence Confirmed (the field is already decoded), severity Moderate-to-Critical depending on how far out of range. Readiness: pure `detect_engine.cpp` wiring against an already-decoded field -- no new decode work.
14. **Modbus read/write quantity out-of-spec** -- grounded in **CVE-2021-22659** (NVD; Rockwell MicroLogix 1400, a buffer overflow from an out-of-spec Read/Write Multiple Coils/Registers quantity value). Modbus's own Application Protocol Specification V1.1b3 defines hard per-function maximums (2000 for Read Coils/Discrete Inputs, 125 for Read Holding/Input Registers, 1968 for Write Multiple Coils, 123 for Write Multiple Registers) -- a request whose `quantity` field (already decoded, per `modbus.hpp`'s `std::optional<uint16_t> quantity`) exceeds its own function's spec maximum is a spec violation regardless of what any specific device's firmware does with it. Distinct from the already-implemented "write outside every range ever read" pattern (that's baseline-relative; this is protocol-conformance-absolute, and fires with no baseline needed). Mapping: `ProtocolMisuse`, **T0855**/**T0831** (Manipulation of Control) depending on read-vs-write, evidence Confirmed, severity Critical (always-notable, N/A novelty -- a spec-violating quantity has no legitimate baseline to be "new" against). Readiness: pure `detect_engine.cpp` wiring against the already-decoded `quantity` field plus a small per-function-code constant table.
15. **OPC UA weak-session pattern** -- grounded in Claroty Team82's own published OPC UA hardening guidance (cited above), which names `SecurityPolicy=None` and anonymous `UserIdentityToken` authentication as the two most consequential network-observable OPC UA misconfigurations. A `CreateSession`/`ActivateSession` exchange whose negotiated security policy URI is `http://opcfoundation.org/UA/SecurityPolicy#None` and/or whose identity token is the anonymous type reaches a server with no encryption, no signing, and no real authentication at all. Mapping: a new "weak/no-auth engineering session" finding (`EngineeringStationActivity` or a new `RemoteAccessChannel`-adjacent category), resolvable between **T0886**/**T0822** with `--policy` the same way the existing remote-access-channel finding already is. Evidence Confirmed (both fields are on-the-wire OPC UA service parameters), severity Moderate (a real exposure, not yet an observed attack), novelty N/A (the weak configuration itself is always worth flagging, independent of who's connecting). Readiness: needs confirming whether conduitscope's existing OPC UA decoder already exposes the negotiated SecurityPolicy URI and UserIdentityToken type on its decoded struct (not verified this session) -- likely a small decode-field-exposure addition rather than new protocol decode work, since OPC UA is already fully in scope.
16. **EtherNet/IP CIP Identity-Object Reset** -- CIP service `0x05` ("Reset"), addressed at the Identity object (class `0x01`) -- confirmed **already decoded and named** by conduitscope's own `src/enip.cpp` (`case 0x05: return "Reset";`, already classified as a `Write`-access service). This service power-cycles or resets the target device, a direct CIP-native analog to DNP3 Cold Restart / S7 PLC Stop / UMAS STOP_PLC. Mapping: `FirmwareLogicChange`, **T0816** (Device Restart/Shutdown), evidence Confirmed, severity Critical, novelty N/A -- same always-notable tier as every other restart-shaped finding already in `DetectEngine`. Readiness: **zero new decode work** -- the service is already named; this is a pure `detect_engine.cpp` wiring addition, the single most implementation-ready item in this whole batch.
17. **EtherNet/IP CIP List Identity/Services/Interfaces broadcast reconnaissance** -- grounded in Léargas Security's own ruleset description ("List Identity/Services/Interfaces recon, external RegisterSession"). conduitscope's `src/enip.cpp` already names and decodes all three encapsulation commands (`ListServices`/`ListIdentity`/`ListInterfaces`, confirmed this session), and `ListIdentity`'s response identity item is already decoded. This is exactly how legitimate engineering tools (RSLinx, Studio 5000) discover CIP devices on a segment -- and exactly how a scanner enumerates one too. Mapping: `EngineeringStationActivity`, **T0888**, evidence Confirmed, new-vs-known novelty resolved the same way the existing CIP-Forward_Open-from-new-originator finding already is. Readiness: **zero new decode work** -- pure `detect_engine.cpp` wiring against already-decoded/named fields.
18. **IEC 60870-5-104 broadcast/global Interrogation** -- grounded directly in the IEC 60870-5-101/104 standard's own definition of the reserved global/broadcast Common Address of ASDU value (`0xFFFF`), and in the academic SCADA-attack literature on IEC 104 command injection found this session (command-injection-style attacks against IEC 104 specifically call out forcing a general interrogation as a disruptive, plant-wide primitive). A General Interrogation (type 100) addressed to the broadcast common address forces *every* RTU on the segment to report full state at once -- a single message with the same kind of outsized blast radius as batch-2's DNP3 broadcast item (#8), but for IEC 104. Mapping: `ProtocolMisuse`, **T0855**, evidence Confirmed (the Common Address field is already tracked per item 3's own `Iec104AsduInfo` work), severity Critical, novelty N/A. Readiness: needs the Common-Address-of-ASDU field checked against `0xFFFF` in `detect_engine.cpp` -- the field itself is already decoded and tracked (per the existing type/COT/IOA-range work), so this is pure wiring, not new decode work.

## Batch 4 -- Digital Bond's remaining protocol-specific rulesets (S7, EtherNet/IP, BACnet, OMRON FINS), sourced fresh this session

Jurgen asked directly ("Do you find more ICS attack patterns?") as a follow-up once Batch 3 shipped. `modbus.rules` and `dnp3.rules` (Batches 1-2) and the CyberICS/nmap/CVE/Claroty material (Batches 2-3) are now fully mined; this batch goes back to Digital Bond's own Quickdraw-Snort repository and reads the protocol-specific rule files that hadn't been fetched yet -- `s7.rules`, `enip.rules`, `bacnet.rules`, and `omron.rules` (all read directly this session, transcribed verbatim below, not summarized from memory), plus `modicon.rules` for completeness even though its own subject (Modbus function code 0x5A, i.e. UMAS) turns out to already be covered. Two more Quickdraw-Snort files exist -- `fox.rules` (Tridium Niagara Fox) and the rest of `modicon.rules` beyond function 90 -- but Niagara Fox is a protocol this codebase doesn't decode at all, so `fox.rules` is out of scope for this pass; noted under "Deliberately not included" below.

Every source below was fetched and read this session, cross-referenced against conduitscope's own decoded fields the same way Batches 1-3 were. Unlike Batch 3 (all fresh decode-field reads), and matching Batches 1-2's own "mostly already decoded" experience, all but one item in this batch (#20's UDP variant) is pure `detect_engine.cpp` wiring against fields already sitting in `S7CommFrame`/`EnipFrame`/`BacnetFrame`/`FinsFrame` today -- confirmed by directly reading `s7comm.hpp`, `enip.cpp`, `bacnet.hpp`, and `fins.hpp`/`fins.cpp` this session, not assumed.

19. **S7 Read SZL enumeration via the Redpoint Nmap NSE script** -- Quickdraw-Snort `s7.rules` SIDs 1111301/1111302, `"S7 Enumerate Redpoint NSE Request CPU Function Read SZL attempt"` (the second SID is the same condition restricted to a non-`$S7_CLIENT` source). Wire condition: an S7 Userdata (ROSCTR `0x07`) PDU whose parameter block is exactly CPU-functions (group `0x04`) / Read SZL (subfunction `0x01`), request direction -- the rule matches the request shape generically, not any specific SZL-ID, so it fires on *any* Read SZL request, not just a Redpoint-tool-specific byte pattern (unlike Batch 2's Metasploit/nmap Modbus fingerprints, which matched fixed transaction/SZL-ID bytes a specific tool always sends). `s7comm.hpp` already decodes Read SZL fully (`S7CommFrame::szl_id`/`szl_id_name`, confirmed by reading the struct this session) -- but `detect_engine.cpp` currently has **no finding for Read SZL at all** (confirmed by grep), a genuine gap next to the CIP-List*/UMAS-READ_ID/FINS-Controller-Data-Read new-originator findings this codebase already has for the exact same "engineering-tool identity/version enumeration" shape on other protocols. Mapping: `EngineeringStationActivity`, **T0888** (Remote System Information Discovery), evidence Confirmed, new-vs-known novelty resolved the same `--baseline-file`/first-occurrence way as the CIP-List*/UMAS-READ_ID findings. Readiness: pure `detect_engine.cpp` wiring against the already-decoded Read SZL request fields, plus a new per-server originator-tracking map (same shape as `enip_list_discovery_originators_by_server_`).
20. **EtherNet/IP List Identity via the Redpoint Nmap NSE script** -- Quickdraw-Snort `enip.rules` SIDs 1111517 (TCP/44818) and 1111518 (UDP/44818), `"EtherNet/IP Request Identity Attempt Via Redpoint Nmap NSE"`. Wire condition: a ListIdentity request (encapsulation command `0x0063`, already named by `enip.cpp`) whose CPF sender-context field is the fixed 4 bytes `C1 DE BE D1` -- Redpoint's own NSE script hardcodes this value, making it a genuine byte-exact tool fingerprint (unlike #19), the same shape as Batch 2's Metasploit/nmap Modbus fingerprints. **The TCP variant is pure wiring** -- `EnipTcpDecoder` already decodes ListIdentity's sender context via the general encapsulation-header path. **The UDP variant needs new decode work first**: confirmed by reading `src/enip.cpp` this session that `EnipUdpDecoder::decode` (`enip_udp_decoder()`) calls `try_parse_cip_io` only -- it never parses the encapsulation-command format at all, so a UDP ListIdentity/ListServices/ListInterfaces packet (the actual real-world discovery mechanism, sent as a UDP broadcast to port 44818 rather than opened per-target over TCP) is invisible today. This is the same UDP gap Batch 3 item 17's own LIMITATIONS bullet already documented for the generic List*-new-originator finding -- implementing UDP encapsulation-command parsing here would close both gaps at once, but it is genuine new decode work (a new UDP-side parse path in `enip.cpp`), not pure wiring, and would need its own fixture/fuzz-corpus treatment like any new decode path. Mapping: `ProtocolMisuse`, **T0888**, evidence Confirmed (byte-exact sender-context match), severity Informational (reconnaissance, not damage) -- distinct from and in addition to Batch 3 item 17's own generic new-originator finding, the same "generic pattern plus a specific tool fingerprint" relationship Batch 1/2's Read-Device-Identification/Report-Server-ID findings have with their own Metasploit/nmap fingerprints. Readiness: TCP half is pure wiring; UDP half needs new decode work, flagged honestly rather than silently skipped or silently claimed as covered.
21. **BACnet foreign-device/broadcast-distribution-table reconnaissance and misuse** -- Quickdraw-Snort `bacnet.rules`, 9 SIDs (1111701-1111709) collapsing into three wire-level shapes once the request/NAK-response and authorized/unauthorized-host pairs are folded together (mirroring how Batch 2 item 8 folded DNP3's authorized/unauthorized broadcast pair into one finding): (a) a **Register-Foreign-Device** request (BVLC function `0x05`) -- a device asking a BBMD to relay broadcasts to it from off its local subnet, the BACnet-native analog of the CIP-List*/S7-Read-SZL/UMAS-READ_ID engineering-tool-presence shape, but specifically a *network-topology* change rather than a data read; (b) a **Read-Foreign-Device-Table** or **Read-Broadcast-Distribution-Table** request (BVLC functions `0x06`/`0x02`) -- reconnaissance against the BBMD's own routing configuration; (c) a **BVLC-Result NAK** (function `0x00`) carrying one of the three matching denial codes -- `0x0030` (Register-Foreign-Device NAK), `0x0020` (Read-Broadcast-Distribution-Table NAK), or `0x0040` (Read-Foreign-Device-Table NAK), values verified directly against Wireshark's own `packet-bvlc.c` `bvlc_result_names` table this session, not assumed -- meaning a request in (a)/(b) was actually refused, real evidence the requester wasn't a legitimate BBMD peer. All three fields (`BacnetFrame::bvlc_function`, `has_result_code`/`result_code`, `has_registration_ttl`) are already decoded per `bacnet.hpp` (confirmed by reading the struct this session) -- zero new decode work. Mapping: (a)/(b) `EngineeringStationActivity`/**T0888**, evidence Confirmed, new-vs-known novelty, severity Informational-to-Moderate ((a) is a topology change, arguably closer to `ProtocolMisuse`/**T0855** than pure reconnaissance -- worth deciding at implementation time whether it's one finding or two depending on whether it succeeds); (c) `ProtocolMisuse`/**T0855**, evidence Confirmed (a NAK is the device's own explicit refusal), severity Moderate, always-notable (a refused foreign-device/table request has no legitimate "new vs. known" axis -- it failed regardless of who sent it). Readiness: pure `detect_engine.cpp` wiring against already-decoded fields, plus one new small `bvlc_result_code_name()`-style lookup (six values, all now verified) if a human-readable NAK reason is wanted in the finding description.
22. **OMRON FINS Controller Data Read from a new originator** -- Quickdraw-Snort `omron.rules` SIDs 1111401-1111404 (TCP/9600 and UDP/9600 variants, each with an authorized/unauthorized-host pair, matching command code `0x0501`). Wire condition: a FINS "Controller Data Read" request -- pulls the target PLC's model/version identification off the wire, the FINS analog of Modbus Read Device Identification / CIP List Identity / S7 Read SZL / UMAS READ_ID. `fins.cpp` already names this exact command (`{0x0501, "Controller Data Read"}`, confirmed by reading the source this session) and already decodes its response body. Mapping: `EngineeringStationActivity`, **T0888**, evidence Confirmed, new-vs-known novelty (same `--baseline-file`/first-occurrence mechanism as every other engineering-tool-presence finding in this codebase). Readiness: pure `detect_engine.cpp` wiring against the already-decoded `command_code`/`command_name` fields, plus a new per-server originator-tracking map -- both TCP and UDP FINS are already decoded by this codebase (confirmed via `fins.hpp`'s own struct), so unlike #20 there is no UDP gap here.
