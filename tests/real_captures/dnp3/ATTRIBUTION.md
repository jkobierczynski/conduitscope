# Provenance of these fixtures

The `.pcap` files in this directory are real DNP3/TCP captures, not synthetic
traffic generated by `tools/make_sample_pcap.py`. They were pulled from the
public test-capture collection at <https://github.com/automayt/ICS-pcap>
(commit `13b7ae335529146b40535c2d7aa756886040d8ad`, 2026-09-15), under its
`DNP3/` directory. That collection is itself an aggregation of long-circulated
ICS/SCADA protocol-dissector test captures; its own README credits, among
others, **digitalbond** (whose `dnp3_test_data_part1`/`dnp3_test_data_part2`
captures are duplicated verbatim at two paths in that repo -- only one copy of
each is kept here), 4SICS/netresec, scadahacker.com, and the Wireshark sample
captures wiki. These are widely-reused, non-sensitive DNP3 protocol test
vectors -- the same role Wireshark's own dissector test suite draws its
sample captures from -- not production/operational traffic, and the source
project exists specifically so protocol-tooling developers can pull them into
their own test suites, which is exactly the use made of them here.

No explicit license file accompanies the source repository or these
individual captures; they are included here on that basis, with this file as
a clear attribution/provenance record, and can be removed on request.

## Why these specific fixtures

`tests/sample_dnp3.pcap` (hand-built, see `tools/make_sample_pcap.py`) covers
the transport/application/object-header/point-value decode logic exactly as
designed -- useful for pinning down exact expected byte layouts, but it can
only ever test what its author thought to construct. These real captures
exercise the parser against actual wire encodings from independent DNP3
stacks:

- `dnp3_select_operate.pcap` / `dnp3_test_data_part2.pcap`: real CROB
  (group 12 variation 1) Select/Operate command sequences, including one
  operate that comes back `status=Not Supported` rather than `Success` --
  confirms the IEEE 1815 control-status-code table isn't just decoding the
  one value the synthetic fixture happens to use.
- `dnp3_test_data_part1.pcap`: a real polling session (93 DNP3 packets) with
  Binary Input (g1v1, bit-packed), Binary Output (g10v2, byte-per-point with
  flags), Counter (g20v5), Internal Indications (g80v1), and absolute
  timestamp (g50v1) objects all appearing in real traffic, not constructed
  fixtures.
- `dnp3_malformed.pcap`: a deliberately corrupted/fuzzed capture (198
  packets, including an unknown group/variation `g255v255` and unsupported
  qualifiers) -- a regression guard that the parser degrades gracefully
  (bounded `ParseError`-style bailout with a note, never a crash or a
  fabricated value) on genuinely malformed input, not just well-formed
  traffic it wasn't expecting.
- The remaining `*_request`/link-status/read/write fixtures are smaller real
  exchanges (several are link-layer-only, `user_data=0`, captured before the
  application-layer payload) that round out coverage of real traffic shapes
  without duplicating what the synthetic fixture already pins down.

None of these captures happened to contain a DNP3 fragment split across more
than one data-link frame (transport `FIN=0`) -- consistent with what was
observed against a large real 4SICS capture during this feature's
development. Multi-data-link-frame reassembly therefore remains untested
against real traffic; see the ROADMAP in `docs/MANUAL.md`.
